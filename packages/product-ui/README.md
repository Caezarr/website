# Wonka Product UI — candidate library

Private, controlled React components for product composition and motion capture. The canonical registry is `design-system/components.json`; the component stories appear under **Product** in both Storybooks.

```tsx
import {ProductTheme, ConnectorCard} from '@wonka/product-ui';
import '@wonka/product-ui/styles.css';

<ProductTheme theme="light">
  <ConnectorCard connector={connector} onAction={connectOrDisconnect}
    onFavorite={toggleFavorite} onConfigure={openConfiguration} />
</ProductTheme>
```

The package is source-only and stays in this monorepo. It uses the canonical `packages/react/src/button.tsx` primitive: consumers must include that directory in their Tailwind content/source scan, as Website and the lab already do. It is not an independently published package. `tokens.css` is generated by `bun run ds:build` from the existing token source; never edit it manually. No second palette, active brand release or package publication is introduced.

## Integration contract

- Components own no API clients, credentials or product stores. Props own data, permissions, selections and lifecycle states; callbacks express intent.
- `AgentBuilder`: controlled `AgentDraft`, eight section IDs, controlled save state. Name/model and connected selected tools are required before saving. Read-only users can inspect accordions but cannot edit. Knowledge, schedule and version slots keep application-specific logic outside the library.
- `TemplateGallery`/`TemplateDetail`: accept the public template shape, locale, permission and loading/clone states. Localized values fall back to public originals. Instructions come from the detail endpoint, not invented demo content.
- `ConnectorCard`: seven connection states, favorite, organization-managed and consume-only. No callback means a disabled control. OAuth/configuration/revocation must be provided by the host application.
- `SettingsWorkspace`: role/feature visibility; `SettingsPanel`: controlled field values and explicit actions. Organization controls require `canManage`. Enforce all permissions on the server too; UI gating is not authorization.
- `ChatComposer`, `ExecutionTrace`, `ChatMessage`, `SharingPanel`: controlled input, execution, streaming character count and access grants. Backend streaming, actions and sharing are adapters to write in WonkaChat.
- `ProductDialog`: native modal, labelled heading, Escape handling, focus restoration and theme context. Fields expose separate label, required, hint and error semantics.
- `MotionStage`: fixed frame/fps metadata, frozen CSS animations. `resolveCaptureFrame` is pure and uses no timers, network, random values or current time.

Use `apps/wonkachat-lab/src/product/ProductExperience.tsx` as a **demo adapter example**, not as production business logic. It uses fictitious people/client data, local mutations and simulated connection/invitation flows. Refresh resets it.

## Styling and assets

Import the CSS once. Tokens are scoped to `.wp` and `data-theme`; light/dark never modify the consumer's root theme. Ship the existing Website `public/fonts` and `public/images` files to preserve typography and connector/brand logos. The lab and Storybook serve them already. Resizing is supported for normal product screens; the clean capture canvas intentionally stays at 1920×1080.

## Validation

Run the repository checks in `AGENTS.md`, plus `bun run --cwd apps/wonkachat-lab build`. The new stories include interaction tests for catalog search, connect/disconnect, builder validation/read-only controls, role-gated settings, invitations, composer submission, approval rejection and modal focus. Global axe checks remain enabled in both themes.

See `design-system/product/README.md` for coverage/provenance and `MOTION.md` for studio capture instructions. This is a draft library ready for review and motion production, not a claim that the live WonkaChat app has migrated to it.
